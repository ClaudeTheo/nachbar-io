1. Vision & Product Core

In one sentence

QuartierApp is a private trust space where seniors, their family, and their neighborhood stay connected — without social-platform mechanics — with a local link to neighborhood information (waste collection, weather, emergencies, public authorities, OSM POIs).

Phase-1 Product

"Family Circle + Neighborhood Info" — no marketplace, no WhatsApp competition, but a curated, protected room. To get in, you need someone already inside (house-number code by mail; no digital-only onboarding).

2. Social Context & Motivation

The Problem

Seniors in Germany face three overlapping crises:

Loneliness

According to the German Federal Institute for Population Research, over 6 million people aged 65+ live alone in Germany. For those 80+, the rate of socially isolated individuals rises above 25 %. WhatsApp is a bridge, but not a neighborhood platform.

Care Gap

5.2 million people require care (PSG II/III) — 84 % are cared for at home, mostly by relatives without digital support. Media usage is heterogeneous; apps often act as a barrier.

Digital Marginalization

Most "senior apps" are care-documentation tools for professionals or emergency buttons — not relationship spaces. QuartierApp positions itself as a relationship space that eases care without becoming a documentation tool.

Loss of Local Structure

Neighborhood as everyday help network is disappearing. QuartierApp aims to digitally rebuild this structure — with hard neighborhood binding (no "friends-of-friends-of-friends" like social networks).

Three Product Principles

  1. Trust before reach. No viral growth, no recommendation pressure. To get in, you need a house-number code delivered by mail.
  2. Utility before features. Better few features seniors immediately understand than a feature firework that confuses.
  3. Safety before convenience. Medication and check-in data are field-encrypted. Parents must approve child-to-child invitations (GDPR Art. 8).

Brand

Tone-of-voice "calm, factual, no startup hype". Brand colors petrol #2e7d5e, anthracite #3d3d50, warm white #fdf8f3. Font Nunito. 8 px grid. Formal address in UI, informal only internally.

5. Security Architecture

QuartierApp operates at MDR-readiness level (IEC 62304 Class B) without medical-device status. That means: architecture and processes are as robust as required for medical devices — but the product itself does not assume any diagnostic or therapeutic function.

Four Defense Layers

Layer 1 — Network & WAF

  • TLS 1.3, HSTS
  • CSP nonces in <script> tags (no unsafe-inline)
  • Closed-pilot middleware (503 default for non-whitelisted paths)
  • Trap system instead of CAPTCHA (honey routes, auth_bruteforce via Upstash)
  • Rate-limiting via Upstash Redis per path category
  • Vercel firewall with founder-IP bypass 93.200.153.4

Layer 2 — Application

  • Hash-only token storage (SHA-256), never plaintext
  • Tokens never in query strings (server logs, browser history, referer)
  • Founder-bypass helper with hard-coded user-ID set
  • Service-role key server-side only, legacy JWT disabled
  • Webhook validation via isValidExternalUrl
  • External links only through SafeExternalLink component

Layer 3 — Database

  • Row Level Security on all tables, default deny
  • BEFORE-UPDATE triggers make 12 columns sticky (is_admin, role, trust_level...)
  • AES-256-GCM field encryption for sensitive columns
  • Audit trail via admin_audit_log and family_setup_audit
  • 11 event types in family-setup audit (SHA-256 hash for IP + User-Agent)
  • Anon-bypass protection even when an RLS policy is accidentally open

Layer 4 — Process

  • Mini-Audit mandatory for any wave touching auth / RLS / admin surface (5-min checklist)
  • Pre-check before new builds (grep on existing infrastructure)
  • Full audit wave before pilot start and at MRR thresholds
  • External pentest planned at MRR > 2,000 €
  • Founder go-ahead required for red-zone actions (push, prod migration, secrets, billing, auth)

Example: Privilege Escalation Protection (Mig 198)

Even if an RLS policy accidentally allowed an anonymous update, the BEFORE-UPDATE trigger would revert the attempt:

UPDATE users
SET is_admin = true, role = 'attacker', trust_level = 'guest'
-- automatically reverted by the trigger
-- 12 columns are sticky: is_admin, role, trust_level,
-- youth_restrictions, youth_registration_status, pilot_role, ...
-- service_role bypasses correctly

Encryption at Rest

  • Sensitive fields: medication entries, check-in messages
  • Format: aes256gcm:v1:<ciphertext> — versioned for key rotation
  • Key storage: Vercel --sensitive env, never dashboard paste (trailing-newline corruption)
  • Implementation: lib/care/field-encryption.ts

doctor_adminPractice administration

super_adminPlatform operations (founder IDs)

Care Privacy: Two Separate Link Tables

caregiver_links

Caregiver-to-senior. Visible: status, heartbeat, check-in. Not visible: full medication history without senior consent. RLS verifies bidirectionality.

family_child_links

Guardian-to-child. Visible: all child data, full access (parental responsibility). Max 5 direct child accounts per guardian, then needs_admin_review.

Family Setup Flow (Mig 197)

  • 3 token types: child_direct, child_friend, senior_setup
  • 6 status states: pending, claimed, revoked, expired, pending_parent_approval, needs_admin_review
  • Hash-only: token_hash, short_code_hash UNIQUE
  • Child-to-child: pending_parent_approval until parent confirms via dedicated API

Pilot Code Model

Exactly one households.invite_code per household. Distributed by mail. No public posting, no multi-/replacement-code inventory for Pilot 0. A deliberate UX lever: if you have a code, you know someone sent it to you.

Generation Modes Constraint

When creating a family-setup token: target_ui_mode IN ('youth','senior','comfort'). The active mode is for self-registration only, never a setup target — this prevents an adult from generating a setup link for themselves.

Recognition Outside-App (Mig 196, apply-go pending)

Language: "voluntary recognition", not "expense reimbursement". A constraint recognition_handling = 'outside_app_only' structurally ensures the app itself does not handle or move money. Recognition types: free, thank_you, suggested_amount (100-5000 cents = 1-50 €), by_agreement.
